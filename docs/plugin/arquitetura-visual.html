Como o harness-creator transforma governança em mecanismo

Um plugin do Claude Code que compila uma especificação de governança em permissões, hooks e instruções que o próprio Claude Code enforça — sem executor próprio, sem chave de API, sem confiar em "o agente vai obedecer".

01 Em 30 segundos

O produto resolve uma pergunta única: como deixar um agente de IA trabalhar horas sem supervisão humana e ainda assim conseguir dormir à noite? A resposta não é instruir melhor — é compilar a política num mecanismo que o host executa.

Fig. 1 — O harness não roda o agente. Ele produz os artefatos que o host já sabe enforçar.
Entrada

Uma spec de governança (política, TDD, orçamento) e um contrato de demanda (o quê + o como), ambos legíveis e aprováveis por um humano.

Transformação

Compilação determinística — mesma entrada, mesma saída. Sem LLM no caminho crítico, auditável byte a byte.

Saída

Governança nativa: o Claude Code bloqueia, pergunta e libera sozinho. O agente não precisa cooperar para a regra valer.

02 Outcomes — o que o projeto entrega

Nove resultados observáveis. Cada um tem um mecanismo concreto por trás, não uma promessa de comportamento.

Governança que o host enforça A política vira permissions + hooks PreToolUse do Claude Code. Não há executor próprio nem chave de API. compiler.py → settings.local.json …o interpretador do hook não resolve (fechado por || exit 2).

Sessão retomável A sessão nasce sabendo onde parou: progresso, contrato, feature pendente e git log injetados no início. session_start.py · progress.md …o humano precisa recontar contexto (é o sintoma que isso elimina).
Kill-switch só do humano Um sentinel desliga todos os hooks. O agente é impedido por regra de floor de criar esse sentinel ou rodar harness disable. killswitch.py …o sentinel fica ligado sem ninguém perceber — por isso harness status.
Fim de demanda determinístico harness finish audita o fecho (evidência fresca, sem resíduo) e só então varre descartáveis. Nunca toca em git. finish.py …a auditoria reprova: o comando reporta e para, sem limpar o rastro.
Princípio de projeto que amarra tudo: sem teatro de enforcement. O que não é enforçável é declarado advisory — o orçamento de tokens, por exemplo, vira orientação no AGENTS.md com a frase explícita de que o Claude Code não expõe contagem de tokens a hooks. Nada finge ser um bloqueio.
Leitura de gestão: o valor não está em "o agente escreve código". Está em reduzir o custo de confiar nele — o humano toca o processo uma vez (aprovar o contrato) e recebe de volta trabalho com prova anexada.

03 O conceito: por que compilar em vez de executar

Abordagem descartada Executor próprio

Um orquestrador que chama a API, roda o modelo em contêiner e aplica política no meio. Custo: infraestrutura, chave de API, Docker, e uma segunda implementação de tudo que o host já faz. Foi o desenho anterior deste projeto — abandonado no pivot de 2026-07.

Abordagem adotada Compilador de governança

O harness produz configuração e hooks; o Claude Code executa. Zero infraestrutura, zero credencial, e o enforcement roda no mesmo processo que faz as tool calls — ponto onde não há como o agente passar por fora.

As três leis do desenho

1 · O repo é a fonte da verdade

Todo estado vive em arquivo. Sessão fria + injeção no SessionStart vence conversa longa — contexto que só existe no chat some no primeiro compact.

2 · Prova executável é a única moeda

"Feito" não é uma afirmação do agente. É um exit_code == 0 gravado com timestamp e hash do conteúdo verificado.

3 · O harness deve barrar o mínimo

Um deny difícil demais empurra o humano para o kill-switch — e o kill-switch é desproteção total. Cada recusa carrega o escape barato na própria mensagem.

Tensão assumida, não escondida: a lei 3 é o contrapeso da lei 2. Toda mensagem de deny do boundary_guard aponta o caminho de saída sancionado (harness task add-file, .harness/scratch/, extra_allowed_commands) justamente para que o operador não desligue tudo.

04 Arquitetura em camadas clicável

Seis camadas. Clique em qualquer uma para ver o que ela contém e qual responsabilidade ela não tem.

Clique numa camada para ver detalhe, responsabilidade e o que ela deliberadamente não faz.
Fig. 2 — Camadas. A seta de autoridade aponta para baixo; a de execução, para cima.

Por que a camada 3 é stdlib puro

Os hooks rodam num processo separado, lançado pelo Claude Code, fora do pacote instalado. Um import harness ali quebraria assim que o venv mudasse. Então o compilador embute o código-fonte dos guards — inclusive o regex derivado do test_glob e o trecho que lê o contrato — em arquivos autocontidos.

A falha mais perigosa que este projeto já diagnosticou: um hook registrado como python "<script>" com o interpretador irresolúvel não roda — e, pela semântica de exit code do Claude Code, a tool call passa sem gate nenhum. O guard falha aberto. A correção mora no lançador, não no script: caminho absoluto do interpretador + sufixo || exit 2, sintaxe comum a sh e cmd.exe.

06 Artefatos: o que é versionado, o que é da máquina

Uma frase resolve toda a política: especificação, contrato e prova são versionados; saída de compilação que carrega dado de máquina é machine-local e regenerada por compile.

Fig. 4 — A fronteira. O .gitignore dessas regras é escrito pelo próprio produto em arquivos tool-owned, nunca no .gitignore da raiz.
Consequência operacional aceita: um clone novo não nasce governado. O repositório clonado tem yaml, contrato e evidência — parece instalado — mas sem settings.local.json nenhum hook roda. É exatamente o que harness doctor existe para gritar.

07 O ciclo completo: Plan → Work → Review

Três raias: o que o humano faz, o que a CLI faz e o que o agente faz dentro da sessão. O único toque humano obrigatório por demanda é o losango de aprovação.

Fig. 5 — O ciclo. Dois portões read-only antes de qualquer escrita (preflight no repo, assess na demanda); e a CLI, não o agente, é quem cria branch, compila contrato e grava evidência.
PLAN

Demanda → contrato aprovável. A skill redige; o humano aprova. Nada compila sem a assinatura no frontmatter.

WORK

Uma feature por vez, dentro do raio declarado, com autocorreção limitada por stop conditions vindas do próprio spec.md.

REVIEW

Prova executável + revisão independente (opcional) + aprovação humana do commit + encerramento auditado da demanda.

08 Diagramas de sequência

O que acontece, mensagem a mensagem, nos três momentos que definem o produto.

O ponto crítico: o gate é enforçado na compilação. compile_contract não escreve um byte se o frontmatter não tiver approved_by e approved_at. Não é uma instrução para a skill obedecer — é uma exceção levantada no código.

O ponto crítico: o guard não confia no cwd do payload — ele se ancora no próprio __file__, que mora sempre em <repo>/.harness/hooks/. Um agente que fez cd e não voltou não desloca a raiz do repositório sob a qual a superfície é avaliada.

O ponto crítico: o feature-lock. Marcar passes:true exige evidência mais nova que o último commit. Uma evidência velha não prova nada sobre o código atual — e o guard nega a edição do feature_list.json citando o id problemático.

09 A cascata de decisão simulador

Todo enforcement do produto cabe numa cascata ordenada. A ordem é a segurança: o piso é avaliado antes de qualquer coisa, inclusive antes de perguntar se existe contrato.

Simulador da decisão

Contrato ativo: atritos-do-ciclo · superfície = src/harness/boundary_guard.py, tests/test_boundary_guard.py, src/harness/cli.py · branch contract/atritos-do-ciclo · test_glob = tests/**/*.py
—
Escolha uma entrada.

    As quatro garantias, em ordem

    1 Runtime floor — incondicional
    Roda antes de tudo. Nega git push (exceto para a branch do contrato ativo), publicação e rede não planejada (curl, wget, npm publish, pip upload, twine upload, gh release, e no PowerShell Invoke-WebRequest/irm), redirecionamento para arquivo de segredo (.env, .pem, id_rsa, *credentials*), criação do sentinel de kill-switch e commit em branch protegida.

    Limite declarado por escrito: o floor de segredo cobre redirecionamento e cmdlets de escrita — não persegue escrita indireta via interpretador (python -c "open('.env','w')"). É corrida armamentista de custo desproporcional para este mecanismo, e está documentado como risco residual aceito, não como lacuna esquecida.

    2 Proteção contra enfraquecimento de teste
    Arquivo que casa test_glob só é editável se alguma tarefa do contrato ativo o declarar em files[]. Substitui o guard estático sempre-ask por uma decisão por tarefa — o humano deixa de aprovar às cegas e passa a ver, na razão do diálogo, qual comportamento aquele teste cobre.
    3 Superfície de documentação
    Escrita sob docs/** é sempre permitida — prosa não quebra teste. Com exclusão explícita de AGENTS.md, CLAUDE.md, Plans.md, spec.md e .harness/harness.yaml: abrir o documento de governança à reescrita livre pelo agente que ele governa foi uma proposta rejeitada.
    4 Superfície de scratch
    .harness/scratch/** é sempre gravável, com .gitignore autocontido. Existe porque screenshots e dumps de verificação não pertencem a files[] de nenhuma tarefa — e, sem um destino sancionado, acabavam soltos na raiz do repositório. O floor de segredo continua precedendo: .harness/scratch/credentials.json segue negado.

    10 Prova executável e revisão independente

    O que é uma evidência

    Não é um relato. É um arquivo com schema fixo, gravado só quando o comando real rodou e saiu 0:

    {
  "feature_id": "T-01",
  "contract":   "atritos-do-ciclo",
  "verify_cmd": "python -m pytest tests/test_boundary_guard.py -k date -q",
  "recorded_at":"2026-07-28T21:40:12+00:00",   ← comparado com o último commit
  "exit_code":  0,
  "files_hash": "sha256:<hex>"              ← conteúdo dos files[] no momento da prova
}
    Feature-lock: marcar passes:true só é permitido se, para cada feature transicionada, existir evidência válida e mais nova que git log -1. Sem isso, o guard nega a edição do feature_list.json citando o id.

    A máquina de estados da revisão

    Padrões de time disponíveis

    producer-reviewer completo

    Produtor escreve, revisor veta. O revisor nunca recebe Edit/Write — é invariante do catálogo, checado pelo audit-team.

    supervisor completo

    Um orquestrador distribui features respeitando depends[]; também sem ferramentas de escrita.

    +4 declarativos

    pipeline, expert-pool, fan-out-fan-in, hierarchical-delegation — templates simplificados.

    Feature-lock estendido: quando o time declara producer+reviewer, passes:true passa a exigir evidência fresca e aprovação do revisor mais recente que a evidência. Aprovação obsoleta frente a uma evidência regravada depois dela → deny.

    11 Piso de segurança e kill-switch

    O paradoxo resolvido

    O humano precisa poder desligar tudo. O agente não pode se desligar. Os dois convivem porque o hook só existe dentro da sessão do Claude Code: o usuário roda harness disable no terminal dele, onde nenhum hook intercepta; o agente que tenta o mesmo comando — ou criar o sentinel por escrita/redirecionamento — bate numa regra de floor.

    O risco que sobra

    Um kill-switch invisível. O guard já ficou em no-op por dias sem sinal nenhum na sessão. A mitigação é operacional, não técnica: só harness status conta a verdade — confira antes de tratar qualquer sessão como evidência de que a governança estava valendo.

    Matriz de política

    Modoreadeditexecutenetwork edit_testQuando usar
    paranoidask askask askask Produção. Aprova literalmente tudo, inclusive leituras.
    balancedallow askask askask Padrão recomendado. Aprova tudo que muda estado.
    autoallow allowallow askask Autonomia total confiada. Rede e teste seguem gateados sempre.

    Rede nunca vai para allow, em nenhum modo. E edit_test não é aprovado automaticamente por política nenhuma — nem em auto.

    Nota de implementação: a matriz não é duplicada no compilador. Ele importa _POLICY_MATRIX e _ALWAYS_GATED de governance/approval.py — fonte única, para as camadas nunca divergirem. O mesmo vale para o glob→regex (patterns.py) e para os critérios de floor, importados por session_permissions.py a partir do boundary_guard.

    13 Diagnóstico: quatro laudos, nenhum conserta sozinho

    harness preflight antes de tudo

    Laudo de prontidão de um repositório cru, read-only. Quatro categorias — Git, Manifestos, Verificação/TDD, Qualidade Estática — cada check não-PASS carregando uma correção acionável. Veredito: READY / READY_WITH_WARNINGS / NOT_READY.

    harness audit drift

    Score 0-100 + findings. Dogfooding deliberado: em vez de reimplementar as regras, recompila em memória e compara com o disco. Qualquer divergência é drift. Exit 1 com qualquer finding crítico.

    harness audit-runtime invariantes

    Audita o que muda durante a execução: schema do feature_list.json, presença do progress.md, evidência correspondente a toda feature marcada como passada, e no máximo uma feature em progresso.

    harness doctor falha silenciosa

    Compara as três camadas de distribuição — pacote pip, .harness/ compilado, cache de plugin do Claude Code — e detecta hook registrado que não roda. São falhas onde nada quebra: o Claude Code apenas roda menos governança do que o repositório aparenta ter.

    14 Roadmap: onde está e para onde vai

    Fig. 8 — Fases 1–4 entregues e em uso (o projeto se governa a si mesmo). Fases 5–7 são backlog documentado.

    Onde a autonomia ainda trava — diagnóstico honesto do próprio projeto

    1 O gate exige humano

    A aprovação do contrato é enforçada só na compilação. Mecanicamente, nada impede um agente de preencher o frontmatter — "a skill nunca se auto-aprova" é instrução, não mecanismo. A Fase 5 fecha isso com risk-tier determinístico + juiz independente + regra de floor sobre o frontmatter.

    2 Não existe driver de loop

    O supervisor é um leitor síncrono deliberado. Ninguém encadeia feature→feature, sessão→sessão. Hoje o orquestrador real só existe dentro do teste E2E.

    3 Nenhum sinal é consumido por máquina

    Orçamento é texto advisory; stop conditions são strings que ninguém conta; o verify só grava sucesso — a falha não deixa rastro estruturado.

    Achado central da investigação: os módulos que resolvem o item 3 não têm dependência dura de Docker nem de chave de API. O que os prendia à era congelada era o sinal que consumiam, não a infraestrutura. A Fase 5–7 é, em essência, re-plumbar esses sinais a partir das primitivas nativas do Claude Code — --max-budget-usd, --resume, --output-format json, hooks Stop/PostToolUse/SubagentStop.

    15 Glossário

    TermoSignificado neste projeto
    HarnessA camada de governança em volta do modelo: permissões, gates, verificação e o ciclo de sessão. Não é o modelo, não é o prompt.
    ContratoO par spec.md (o quê: escopo, critérios, stop conditions) + Plans.md (o como: tarefas, arquivos, comando de verificação). É o único artefato que um humano aprova.
    Raio de impactoO conjunto de arquivos e comandos que o contrato ativo autoriza. Fora dele, o guard nega.
    Runtime floorO piso incondicional: o que nunca vira allow, com ou sem contrato. Avaliado antes de qualquer outra coisa.
    Feature-lockA regra que impede marcar uma tarefa como concluída sem evidência fresca (e, com time, sem aprovação do revisor mais recente que a evidência).
    EvidênciaJSON com o resultado real do verify_cmd: comando, timestamp, exit code e hash do conteúdo verificado.
    DriftDivergência entre a spec e o que está compilado em disco. Detectado por recompilação em memória + comparação.
    Machine-localArtefato que carrega dado desta máquina (path absoluto) e por isso nunca viaja no git — é regenerado por compile.
    BootstrapO estado sem contrato compilado. A superfície de escrita segue negada; a de comando abre o mínimo para criar o primeiro contrato.
    Stop conditionO disjuntor do loop de autocorreção, declarado no frontmatter do spec.md. Satisfeita qualquer uma, o agente para e devolve o controle.
    Progressive disclosurePadrão usado no AGENTS.md: bloco curto no arquivo lido sempre, detalhe completo num arquivo apontado.
    DogfoodingO projeto se governa com o próprio harness. Os contratos em .harness/work/ deste repositório são o histórico real de uso.
